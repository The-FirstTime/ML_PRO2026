## 2. Поды в `ImagePullBackOff` при зелёном прогоне job `deploy`

Это не ошибка, а ожидаемое промежуточное состояние, возникающее из-за порядка
шагов в `ci.yml`:

`ImagePullBackOff` - поды - это поды от первого, заведомо
неправильного `apply`, которые существуют считаные секунды до `set image` и
не влияют на итоговый результат `rollout status`.

## 3. Путь пароля базы: от GitHub Settings до переменной окружения в поде

1. **GitHub → Settings → Secrets and variables → Actions** — туда вручную
   добавляется секрет `DB_PASSWORD`.
2. В `ci.yml`, шаг `подтягиваем секреты` job `deploy`, значение читается через
   `${{ secrets.DB_PASSWORD }}` и кладётся в переменную окружения раннера
   `DB_PASSWORD`
3. Этим значением формируется **Kubernetes Secret** внутри kind-кластера:

4. `k8s/deployment.yaml` подключает этот Secret к поду через:
```yaml
   envFrom:
     - secretRef: {name: spam-secrets}
```
5. При старте пода **kubelet** читает объект Secret из etcd (значения там
   хранятся в base64, не в открытом тексте на диске пода) и инжектит ключи
   (`POSTGRES_PASSWORD`, `DATABASE_URL`) как переменные окружения внутри
   контейнера — именно их потом читает `pydantic_settings.BaseSettings` в
   `spam/config.py` (`database_url: str | None`).

**Почему нельзя в `configmap.yaml`:**
- `configmap.yaml` — обычный файл в git-репозитории. Если положить туда пароль,
  он окажется в истории коммитов **навсегда**, доступный каждому, у кого есть
  доступ к репозиторию (и любому форку) — именно от этого и защищают секреты
  GitHub Actions, которые в репозиторий не попадают вовсе.
- ConfigMap в Kubernetes предназначен для **несекретных** данных конфигурации
  и хранится так же открыто, как любой другой ресурс — его легко прочитать
  командой `kubectl get configmap spam-config -o yaml` без специальных прав.
  Secret — отдельный тип ресурса с собственной RBAC-семантикой (можно
  ограничить доступ `get`/`list` к `secrets` отдельно от `configmaps`), и при
  включённом encryption-at-rest в кластере его значения шифруются в etcd, в
  отличие от ConfigMap.
- Итог: ConfigMap = "что не страшно показать", Secret = "что нужно
  ограничивать и не хранить в git".

## 4. Если убрать `needs: tests` у job `build`


`needs: tests` гарантирует, что `build` стартует только после **успешного**
завершения job `tests`. 
Если убрать `needs: tests`, `build` триггерится независимо от `tests` —
по тому же событию (`push` в `main`), и может стартовать **параллельно** с
`tests` или даже раньше, чем `tests` успеет упасть.

## 5. Почему на pull request бегут только `tests`

Отвечает строка:
```yaml
build:
  needs: tests
  if: github.ref == 'refs/heads/main'
```
`tests` триггерится всегда (и на `push`, и на `pull_request`. У `build` стоит условие `if: github.ref == 'refs/heads/main'`, поэтому `build` **пропускается** (помечается `skipped`, `deploy` формально зависит от
`build` (`needs: build`), а job, зависящий от пропущенного job, по умолчанию
тоже пропускается — значит, и `deploy` на PR не выполняется.

**Зачем так сделано:**
- На PR ещё нет финального кода — собирать и пушить образ в `ghcr.io`, а тем
  более выкатывать его куда-либо, для непромерженного кода бессмысленно и
  расходует ресурсы/квоту GHA на каждый коммит в каждом PR.
- Секреты (`secrets.GITHUB_TOKEN` с правом `packages: write`, `secrets.DB_PASSWORD`)
  по умолчанию **недоступны** воркфлоу, запущенным из PR сторонних контрибьюторов
  (форков) — значит, `build`/`deploy` там и не смогли бы отработать, упав с
  ошибкой авторизации; условие на `main` явно и заранее исключает такой провал.
- Быстрая обратная связь на PR важнее: `tests` достаточно, чтобы ревьюер понял,
  ломает ли PR код, не дожидаясь сборки образа.

## 6. Зачем `pg_advisory_xact_lock` в `init()`

**Реплики здесь — это поды Deployment `spam-service`**, у которых 2. Каждая реплика при старте приложения
выполняет `lifespan()` → `db.init()` **независимо и параллельно** с другой.

Поэтому `pg_advisory_xact_lock(1)` — блокирует на уровне
сессии/транзакции Postgres. Так при одновременном старте двух
реплик одна из них получит лок первой и спокойно выполнит
`CREATE TABLE IF NOT EXISTS`, а вторая будет ждать на этом же логе, пока
первая не закоммитит транзакцию 

## 7. Порядок статусов пода в жизненном цикле

Без доступа к конкретным трём красным прогонам не могу сказать, какие именно
статусы видели вы — приведу канонический порядок состояний пода, по нему
легко сопоставить ваши три случая:

1. **`Pending`** — под создан в API Kubernetes, но ещё не запланирован
   (scheduler не нашёл/не назначил node) **или** назначен на node, но
   контейнер ещё не начал создаваться (например, ждёт `PersistentVolume`,
   или на node банально не хватает ресурсов под `resources.requests`).
2. **`ContainerCreating`** — node назначена, kubelet начал готовить
   контейнер: тянет образ, монтирует секреты/конфигмапы/volume. 
3. **`Running`** — контейнер успешно стартовал, процесс в нём запущен.
   Под на этом этапе может быть `Running`, но ещё **`NotReady`**, если
   `readinessProbe` (`GET /ready`) не проходит — например, `lifespan()` ещё
   не успел отработать `db.init()`/загрузить `model_bundle.joblib`.
4. **`CrashLoopBackOff`** — контейнер стартовал, но упал (например,
   необработанное исключение при `joblib.load`, или гонка из вопроса 6), и
   Kubernetes циклически пытается перезапустить его с экспоненциальной
   задержкой.

Если пришлёте, в каких статусах реально были поды в трёх ваших красных
прогонах (`kubectl get pods` из шага "диагностика" в логе), сопоставлю каждый
с конкретным шагом workflow, который к нему привёл.
